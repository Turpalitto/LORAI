# PREMIUM QUALITY & READINESS AUDIT
# Финальная приёмка дизайна, ощущения премиальности и готовности к реальному использованию

================================================================
РОЛЬ
================================================================

Ты — одновременно: (1) арт-директор из топовой продуктовой студии, работавшей
над медицинскими приложениями уровня UpToDate, Epocrates, Figma, Linear;
(2) senior product reviewer, проводящий финальную приёмку перед вручением
продукта заказчику; (3) дотошный QA, которого не устраивает "работает, но
выглядит как студенческий проект".

Твоя задача — не найти баги (это сделал `AUDIT_BRIEF.md`), а оценить
ВПЕЧАТЛЕНИЕ, ОЩУЩЕНИЕ и ГОТОВНОСТЬ продукта к тому, чтобы врач открыл его
и подумал "вау, это сделано профессионально", а не "ну, сойдёт".

Работай полностью автономно. Для каждой находки ниже среднего балла —
НЕ просто фиксируй проблему, а САМ исправляй код/дизайн/копирайт, пересобирай
приложение, проверяй снова. Повторяй цикл до тех пор, пока итоговый балл по
каждой категории не достигнет порога готовности (указан в рубрике ниже),
либо пока улучшение технически невозможно в рамках стека — тогда фиксируй
в `docs/KNOWN_ISSUES.md` с honest-оценкой, без приукрашивания.

Будь максимально придирчив. Представь, что продукт сейчас покажут главному
врачу клиники, который видел десятки медицинских приложений и мгновенно
замечает халтуру: неровные отступы, несогласованную типографику, топорные
анимации, неуклюжие формулировки, долгую загрузку без обратной связи.

================================================================
МЕТОДОЛОГИЯ
================================================================

Для каждой категории:
1. Пройди по ВСЕМ экранам приложения (список — в разделе "Карта экранов" ниже),
   реально запустив его на эмуляторе/устройстве — не оценивай по коду,
   оценивай по тому, что РЕАЛЬНО видно и ощущается при использовании.
2. Поставь оценку от 0 до 10 по каждому критерию в категории.
3. Для каждой оценки ниже 8 — опиши конкретную проблему, исправь её,
   пересобери приложение, оцени заново.
4. Веди `docs/PREMIUM_AUDIT_REPORT.md` с таблицей оценок "до" и "после"
   исправлений.

Итоговая оценка продукта = среднее по всем категориям.
**Порог готовности к релизу: не ниже 8.5/10 по каждой категории,
общий средний балл не ниже 9.0/10.** Если после разумного количества
итераций (ориентир — до 15 итераций улучшений на категорию) порог не
достигнут по объективным ограничениям стека/времени — зафиксируй честно,
не занижай критерии оценки, чтобы "натянуть" цифру.

================================================================
КАТЕГОРИЯ 1. ВИЗУАЛЬНАЯ СОГЛАСОВАННОСТЬ (вес в общей оценке: высокий)
================================================================

Оцени 0-10 по каждому пункту:
[ ] Единая система отступов (8pt grid или аналог) — нет "случайных" чисел
    вроде padding 13px рядом с padding 16px на соседнем экране
[ ] Единая типографическая шкала (не более 5-6 размеров шрифта на всё
    приложение, чёткая иерархия заголовок/подзаголовок/тело/caption)
[ ] Единая цветовая палитра строго из дизайн-токенов (не захардкожены
    случайные HEX-цвета в отдельных виджетах мимо темы)
[ ] Консистентность компонентов: все кнопки одного типа выглядят одинаково
    на всех экранах (радиус скругления, высота, тени, состояния
    hover/pressed/disabled)
[ ] Консистентность иконографии: один стиль иконок (либо все outline, либо
    все filled — не вперемешку), единый размер в одинаковых контекстах
[ ] Выравнивание элементов: нет визуально "съехавших" на пиксель-два
    элементов относительно соседних (проверяй внимательно на скриншотах)
[ ] Правильная работа Safe Area/notch/статус-бара на разных устройствах —
    контент не наезжает на системные элементы
[ ] Единообразие карточек/контейнеров (тени, скругления, границы) по всему
    приложению

================================================================
КАТЕГОРИЯ 2. ОЩУЩЕНИЕ ПРЕМИАЛЬНОСТИ И БРЕНДА
================================================================

[ ] Есть ли у приложения узнаваемый визуальный "почерк", или оно выглядит
    как дефолтный Material-шаблон без доработки? (Material 3 — это основа,
    но премиальные приложения всегда имеют поверх неё авторские акценты:
    фирменный акцент-цвет, характерная форма элементов, уникальные
    иллюстрации для пустых состояний)
[ ] Есть ли продуманный app icon (не дефолтная иконка Flutter), адаптивная
    иконка под Android (adaptive icon с правильным foreground/background)?
[ ] Есть ли кастомный splash screen (не белый экран с дефолтным лого фреймворка)?
[ ] Иллюстрации/графика для пустых состояний и онбординга — осмысленные
    и качественные (медицинская тематика, ЛОР-специфика: ухо/горло/нос
    иконография к месту), а не generic-стоковые картинки не по теме?
[ ] Качество и профессиональность микротекстов (microcopy): заголовки
    кнопок, подсказки, сообщения об ошибках — написаны ли они живым,
    профессиональным медицинским языком, а не техническим "Error: null"
    или калькой с английского?
[ ] Соответствует ли общий тон приложения медицинской сфере: спокойствие,
    точность, доверие — а не "стартаперская" яркость/игривость, неуместная
    для врача на приёме?
[ ] Сравни субъективно с эталонами (UpToDate, Epocrates, DynaMed, Figma,
    Linear) по ощущению "вылизанности" — честно оцени разрыв и закрой его
    насколько возможно в рамках Flutter/Material 3

================================================================
КАТЕГОРИЯ 3. МИКРОВЗАИМОДЕЙСТВИЯ И АНИМАЦИИ
================================================================

[ ] Переходы между экранами плавные (используется `go_router` с осмысленными
    transition-анимациями, а не мгновенная резкая смена экрана)
[ ] Skeleton-загрузчики вместо голых спиннеров на экранах со списками/данными
[ ] Haptic feedback на ключевых действиях (подтверждение расчёта, отправка
    сообщения, успешная загрузка документа)
[ ] Анимация появления ответа ассистента в чате (постепенное появление
    текста/карточек источников, а не резкий "прыжок" контента)
[ ] Pull-to-refresh реализован там, где уместно (списки протоколов, история)
[ ] Состояния кнопок (нажатие/загрузка/disabled) визуально отличаются и
    анимированы (ripple-эффект, изменение на спиннер при async-действии)
[ ] Нет "дёрганий" интерфейса (layout jumps) при подгрузке контента —
    используются placeholder'ы фиксированного размера
[ ] Частота кадров (проверь через Flutter DevTools Performance overlay) —
    стабильные 60fps на списках и анимациях, без джанка при скролле

================================================================
КАТЕГОРИЯ 4. ТЕКСТОВОЕ СОДЕРЖИМОЕ И ТОН (CONTENT QUALITY)
================================================================

[ ] Все тексты в интерфейсе вычитаны: нет опечаток, нет "campus"-переводов,
    единообразная терминология (например, "клиническая рекомендация"
    используется последовательно, а не вперемешку с "протокол"/"рекомендация"
    без системы)
[ ] Сообщения об ошибках человечны и действенны: не "Error 500", а "Не
    удалось получить ответ. Проверьте соединение и попробуйте снова"
    с кнопкой повтора
[ ] Пустые состояния не просто "Нет данных", а направляют пользователя
    к действию ("Вы ещё не искали протоколы. Начните поиск по МКБ-10
    или названию заболевания")
[ ] Дисклеймеры сформулированы профессионально-юридически корректно,
    не выглядят как вставленная "для галочки" фраза
[ ] Онбординг (если реализован) написан кратко, по существу, без
    маркетингового "воды"
[ ] Названия пунктов меню и кнопок единообразны по длине и стилю
    (не "Рассчитать дозировку" рядом с "Чек-лист" без глагола)

================================================================
КАТЕГОРИЯ 5. ВОСПРИЯТИЕ ПРОИЗВОДИТЕЛЬНОСТИ
================================================================

(Это не функциональная проверка скорости, а именно ОЩУЩЕНИЕ быстроты)
[ ] Время от тапа до визуальной реакции интерфейса — не более 100мс
    (даже если реальный ответ сервера дольше — должна быть мгновенная
    визуальная обратная связь: нажатие кнопки, появление skeleton)
[ ] Холодный старт приложения — замерь реальное время от тапа по иконке
    до интерактивного Dashboard, сравни с ориентиром премиальных приложений
    (цель: до 2 секунд на среднем устройстве)
[ ] Размер APK — проверь итоговый размер релизной сборки, если неоправданно
    большой (>80-100MB без явной причины типа офлайн-моделей) — оптимизируй
    (tree-shaking иконок, сжатие ресурсов, отложенная загрузка ML-моделей
    типа OCR при первом использовании, а не включение в APK)
[ ] Память: проверь через DevTools, нет ли явных утечек памяти при
    длительном использовании чата (накопление сообщений без виртуализации
    списка — исправь на `ListView.builder`/аналог, если ещё не используется)
[ ] Батарея: голосовой ввод, фоновая синхронизация не должны агрессивно
    расходовать батарею — проверь, что WorkManager-задачи имеют разумный
    интервал, а не polling каждую минуту

================================================================
КАТЕГОРИЯ 6. ACCESSIBILITY (доступность)
================================================================

[ ] Достаточный цветовой контраст текста (WCAG AA минимум, 4.5:1 для
    обычного текста) — проверь на всех экранах, особенно в тёмной теме
[ ] Поддержка TalkBack (Android screen reader) — ключевые элементы имеют
    осмысленные semantic labels, не просто "Button 1"
[ ] Минимальный размер тач-таргетов — не менее 48x48dp для всех
    интерактивных элементов
[ ] Поддержка увеличенного системного шрифта без обрезания текста/поломки
    вёрстки на критичных экранах
[ ] Достаточная контрастность и размер для пользователей старшего возраста
    (значительная часть врачей) — не мельчи текст ради "воздуха" в дизайне

================================================================
КАТЕГОРИЯ 7. ГОТОВНОСТЬ К РЕАЛЬНОМУ ИСПОЛЬЗОВАНИЮ (Production Readiness)
================================================================

[ ] Приложение не падает при стресс-тестировании: быстрые повторные тапы,
    резкие повороты экрана во время загрузки, сворачивание/разворачивание
    приложения в момент сетевого запроса, потеря сети посреди действия
[ ] Корректная обработка всех HTTP-ошибок сервера (400/401/403/404/500/timeout)
    с понятным UI-откликом на каждый случай, а не общий "что-то пошло не так"
[ ] Версионирование приложения настроено (versionCode/versionName в
    `build.gradle`), есть экран "О приложении" с версией для техподдержки
[ ] Логирование критических ошибок (хотя бы локальное, с возможностью
    экспорта пользователем для отправки в поддержку) — проверь, что
    реализовано и работает
[ ] Процесс обновления приложения задокументирован (как раскатать новую
    версию APK внутри клиники — через MOBILE_BUILD_GUIDE.md)
[ ] Иконка и название приложения на устройстве выглядят профессионально
    (не "mobile_app" как название на экране запуска)
[ ] Проверена работа на реальном физическом устройстве Android (не только
    эмулятор) — если нет доступа к физическому устройству, явно зафиксируй
    это ограничение в отчёте

================================================================
КАТЕГОРИЯ 8. СРАВНИТЕЛЬНЫЙ БЕНЧМАРК
================================================================

Проведи честное сравнение (в виде таблицы в отчёте) по 5-бальной шкале
относительно референсных приложений по памяти (UpToDate, Epocrates,
хорошо сделанные Material 3 приложения) по осям:
- Визуальная полировка
- Скорость/отзывчивость
- Качество микротекстов
- Доверие/профессиональное ощущение
- Удобство в "полевых" условиях (быстрый доступ к информации на приёме)

Если по какой-то оси разрыв критический — это приоритет №1 для исправления,
даже если остальные категории уже прошли порог.

================================================================
ИТЕРАТИВНЫЙ ЦИКЛ ИСПРАВЛЕНИЯ
================================================================

Для каждого найденного несоответствия:
1. Зафиксируй проблему конкретно (скриншот/описание/экран/компонент)
2. Исправь код/ассеты/копирайт
3. Пересобери (`flutter build apk` при необходимости полной проверки,
   либо hot reload для быстрой итерации в debug)
4. Проверь исправление визуально ещё раз
5. Обнови оценку в таблице отчёта
6. Переходи к следующей проблеме

Приоритизация исправлений при ограниченном времени:
1. Сначала — всё, что в Категории 7 (Production Readiness) и Категории 6
   (Accessibility) — это неприемлемо низкое качество, если не исправлено
2. Затем — Категория 1 (визуальная согласованность) — системные проблемы,
   влияющие на всё приложение сразу
3. Затем — Категории 3, 5 (анимации, производительность)
4. Затем — Категории 2, 4 (премиальность, контент) — финальная полировка
5. Категория 8 — сквозная, обновляется по мере исправления остальных

порогов готовности, веди отчёт. Не останавливайся и не спрашивай подтверждений.
По завершении выведи итоговое содержимое `docs/PREMIUM_AUDIT_REPORT.md`
и финальный вердикт готовности продукта в чат.

Полная цепочка промтов для проекта:
- AGENT_BRIEF.md — строит backend + Flutter-приложение с нуля
- AUDIT_BRIEF.md — проверяет функциональную корректность, безопасность, anti-hallucination
- EXCELLENCE_BRIEF.md — добавляет продвинутые фичи и "умность"
- PREMIUM_AUDIT_BRIEF.md — финальная приёмка дизайна, ощущения и готовности к реальной эксплуатации

Это закрывает полный цикл: от нуля → до рабочего → до умного → до премиального и готового к вручению врачам.

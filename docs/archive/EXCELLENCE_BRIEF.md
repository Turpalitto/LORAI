# EXCELLENCE BRIEF
# Превращение рабочего MVP в выдающийся продукт для ЛОР-врачей

================================================================
КОНТЕКСТ
================================================================

Базовая версия продукта уже реализована (`AGENT_BRIEF.md`) и прошла аудит
(`AUDIT_BRIEF.md`) — она функционально корректна и безопасна. Твоя задача теперь —
не "починить", а СДЕЛАТЬ ПРОДУКТ ВЫДАЮЩИМСЯ: таким, которым врач захочет
пользоваться каждый день, который ощущается как профессиональный медицинский
инструмент топ-уровня (сравнимый по качеству с UpToDate, но заточенный под
российские клинические рекомендации и ЛОР-специфику), а не как учебный проект.

Работай полностью автономно, без вопросов, по всем этапам последовательно.
Для каждого архитектурного решения фиксируй обоснование в `docs/DECISIONS.md`.
Не ломай уже работающий функционал — каждое улучшение сопровождай регрессионным
тестом существующего поведения.

================================================================
ФИЛОСОФИЯ УЛУЧШЕНИЙ
================================================================

Приоритет улучшений именно в таком порядке:
1. Клиническая польза и точность — важнее красоты
2. Скорость работы врача (секунды на приёме решают) — важнее богатства фич
3. Доверие (прозрачность источников, уверенность в данных) — важнее "вау-эффекта"
4. Визуальный полиск и приятность использования — в последнюю очередь,
   но тоже обязательно

Не добавляй фичи ради фич. Каждое улучшение ниже должно либо ускорять работу врача,
либо повышать точность/доверие, либо расширять клиническую полезность.

================================================================
ЭТАП 1. ИНТЕЛЛЕКТУАЛЬНЫЙ СЛОЙ (повышение "ума" ассистента)
================================================================

- [ ] **Кросс-документный синтез**: если вопрос врача затрагивает несколько
  клинических рекомендаций одновременно (например, дифдиагностика между
  состояниями из разных документов) — ассистент должен уметь сопоставлять данные
  из нескольких источников в одном ответе, явно указывая, какая часть ответа
  из какого документа
- [ ] **Проверка лекарственных взаимодействий**: если в базе есть данные о
  нескольких препаратах, добавь модуль проверки совместимости/взаимодействий
  на основе того, что явно указано в контраindications разделах протоколов
  (без домысливания фармакологии вне базы знаний)
- [ ] **Умные уточняющие вопросы**: если запрос врача неполный/неоднозначный
  (например, не указан возраст пациента при вопросе о дозировке) — ассистент
  должен сначала задать уточняющий вопрос, а не гадать или отвечать общё
- [ ] **Семантическое ранжирование дифдиагностики**: улучши модуль
  дифференциальной диагностики — вместо простого совпадения по ключевым словам,
  используй взвешенное ранжирование по количеству совпавших патогномоничных
  признаков из каждого протокола, с визуализацией "почему именно эта нозология
  на первом месте"
- [ ] **Обнаружение противоречий в базе**: если два загруженных документа дают
  разные рекомендации по пересекающейся теме (например, разные версии одной
  рекомендации) — система должна явно подсвечивать это противоречие врачу,
  а не молча выбирать один источник
- [ ] **Автоматическое построение связей между нозологиями**: построй граф
  связей "похожие состояния / частые осложнения / дифдиагнозы" на основе
  содержимого протоколов, используй его для раздела "Похожие протоколы" на
  странице каждой нозологии
- [ ] **Контекстная память в чате**: диалог должен помнить предыдущие сообщения
  в рамках сессии (например, "а какая дозировка для ребёнка 5 лет" после вопроса
  про взрослого пациента — должно понять контекст препарата из предыдущего сообщения)

- [ ] **Свайп-жесты над ответом**: копировать/избранное/печать прямо в списке сообщений

- [ ] **Split-screen для планшетов**: список слева, карточка справа (`LayoutBuilder`)

================================================================
ЭТАП 3. ВИЗУАЛЬНЫЙ И UX-ПОЛИСК
================================================================

- [ ] Редизайн под профессиональный медицинский стандарт: спокойная цветовая
  палитра (синие/зелёные тона, ассоциирующиеся с медициной и доверием),
  высокая читаемость шрифтов, достаточный контраст (WCAG AA минимум)
- [ ] Микроанимации, не отвлекающие, но дающие ощущение отклика системы
  (плавные переходы, skeleton loaders вместо спиннеров, оптимистичные обновления UI)
- [ ] Визуализация уверенности ответа: цветовая индикация (зелёный/жёлтый/серый)
  для high/medium/low confidence ответов ассистента и extraction_confidence
  документов
- [ ] Интерактивная карточка протокола: сворачиваемые секции, якорная навигация
  по разделам, прогресс-бар чтения для длинных протоколов
- [ ] Красивая и функциональная печатная/PDF-версия чек-листов и заключений
  (отдельный print-stylesheet, логотип/шапка клиники — настраиваемая)
- [ ] Информативные пустые состояния (empty states) и понятные сообщения об
  ошибках везде, где раньше могли быть просто пустые экраны
- [ ] Адаптивная типографика и верстка под планшет (врачи часто используют
  планшеты в кабинете)
- [ ] Онбординг для нового пользователя: интерактивный тур по ключевым функциям
  при первом входе (3-5 шагов, пропускаемый)

================================================================
ЭТАП 4. АНАЛИТИКА И САМООБУЧЕНИЕ СИСТЕМЫ
================================================================

- [ ] **Дашборд использования** (для администратора клиники): какие протоколы
  запрашиваются чаще всего, какие вопросы чаще всего получают "нет данных"
  (сигнал о пробелах в базе знаний — нужно догрузить документы), среднее время
  ответа
- [ ] **Обратная связь по ответам**: кнопки 👍/👎 под каждым ответом ассистента,
  накопление для последующего анализа качества (без изменения модели "на лету" —
  просто сбор данных для улучшения промтов/базы)
- [ ] **Выявление пробелов в базе знаний**: автоматический отчёт о темах, по
  которым врачи часто спрашивают, но система честно отвечает "нет данных" —
  это прямой сигнал, какие клинические рекомендации нужно догрузить
- [ ] **Журнал клинических обновлений**: при загрузке новой версии документа,
  взамен старой — автоматически генерируемый diff-отчёт "что изменилось в
  рекомендациях" (сравнение структурированных JSON старой/новой версии)

ЭТАП 5. РАСШИРЕННАЯ КЛИНИЧЕСКАЯ ФУНКЦИОНАЛЬНОСТЬ
================================================================

- [ ] **Калькулятор рисков/шкал**, если применимо к ЛОР (например, шкалы оценки
  тяжести, используемые в загруженных протоколах) — реализуй как интерактивные
  формы с автоматическим расчётом и интерпретацией результата согласно протоколу
- [ ] **Визуальные атласы/схемы** (если в PDF есть изображения/схемы — извлекай
  их отдельно при обработке PDF и прикрепляй к соответствующим разделам протокола,
  а не только текст)
- [ ] **Модуль мониторинга пациента**: для хронических состояний — генерация
  плана динамического наблюдения (follow_up) с напоминаниями о контрольных
  сроках на основе данных протокола
- [ ] **Сравнение протоколов**: возможность выбрать 2 нозологии и увидеть их
  бок о бок (диагностика, лечение) — полезно при дифдиагностике похожих состояний
- [ ] **Экспорт в формат ЕГИСЗ/МИС-совместимый** (если применимо) — хотя бы
  базовый структурированный экспорт заключений в формате, который легко
  интегрировать с распространёнными медицинскими информационными системами
  (HL7 FHIR как минимум в виде заготовки/абстракции на будущее)

ЭТАП 6. НАДЁЖНОСТЬ И PRODUCTION-GRADE КАЧЕСТВО
================================================================

- [ ] Мониторинг здоровья системы: эндпоинт `/health` с детальной проверкой
  всех зависимостей (БД, векторное хранилище, доступность LLM API),
  dashboard статуса для администратора
- [ ] Структурированное логирование (JSON logs) с уровнями, корреляционными
  ID запросов для трассировки проблем
- [ ] Graceful degradation: если LLM API недоступен — система всё равно должна
  работать в режиме прямого поиска по структурированной базе (`/search-protocol`),
  с понятным уведомлением "чат временно недоступен, используйте прямой поиск"
- [ ] Резервное копирование: скрипт автоматического бэкапа PostgreSQL +
  векторной БД, инструкция восстановления
- [ ] Нагрузочное тестирование: симуляция 50-100 одновременных запросов к
  `/chat` и `/search-protocol`, оптимизация узких мест (кэширование частых
  запросов, connection pooling)
- [ ] Оптимизация стоимости LLM-вызовов: кэширование одинаковых/похожих
  запросов (semantic cache), чтобы не делать повторный дорогой вызов API
  на идентичные вопросы
- [ ] **WorkManager-синхронизация (mobile, вместо PWA/Service Worker)**:
  периодическая фоновая задача обновления кэша топ-N протоколов

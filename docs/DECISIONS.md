## #27 (2026-10-07): аудит разметки разделов, фильтрация библиографии, порог эмбеддингов 0.75
- Повод: замер показал «покрытие разделов 1.000», но это метрика против НАШИХ ЖЕ меток. Ручная проверка (`scripts/check_section_labels.py`) выявила, что детектор заголовков «дребезжал»: 80 переключений раздела на 168 чанков одного протокола, метка `definition` стояла на тексте лечения, а `prevention` — на списке литературы (лексическое совпадение 21 %).
- Причина дребезга: правило «строка < 80 символов содержит ключевое слово» срабатывало на обычных коротких строках. Исправлено на строгое: строка ЦЕЛИКОМ равна названию главы (с необязательной нумерацией и двоеточием), список глав задан явно. Результат: 6–7 переключений на документ (по числу реальных глав), лексический индикатор: treatment 99 %, diagnostics 88 %, referral 87 %, prevention 21 % → 72 %.
- Найдено следствие: глава «Источники и литература» не распознавалась, поэтому ~140 чанков библиографии числились разделом `prevention` и могли попадать в «источники» ответа. Введён фильтр: строки-колонтитулы (дата печати, крошки MedElement, URL, номера страниц) и библиографические строки в индекс не идут, глава литературы выбрасывается целиком. Индекс 1899 → 1084 чанка; проверено, что клинический текст не потерян (символов 99 % от исходного).
- Порог эмбеддингов снижен 0.80 → 0.75: два реальных ЛОР-вопроса имели скор 0.797 и получали ложный отказ. Скор у e5 домены не разделяет (вне-доменные 0.826–0.855, in-domain 0.797–0.91) — разделяет домен-гейт, поэтому порог нужен лишь как «совсем ничего не найдено» и не должен отсекать реальные вопросы. Проверено: ложные отказы 0.000, вне-доменные 1.000.
- Гибридное ранжирование (эмбеддинги + лексический TF-IDF, `HYBRID_WEIGHT=0.15`) включено по out-of-sample результату на hold-out: recall@6 0.727 → 0.818, «протокол+раздел» 0.727 → 0.818 при MRR 0.844 → 0.787; в score для врача и гейта остаётся честный косинус.
- Hold-out набор (`data/eval/lor_retrieval_holdout.json`, 22 вопроса + 5 вне-доменных, составлен после настройки и для неё не использовался) и LLM-судья (`scripts/eval_answers.py --judge`) добавлены как постоянный инструмент: словесные формулировки врача — главный источник провалов TF-IDF (ложные отказы 63 % против 0 % у эмбеддингов).

## #29 (2026-10-21): JWT остаётся в localStorage — осознанный компромисс
- Факт: access/refresh-токены хранятся в `localStorage` (`frontend/src/lib/storage.ts`), значит доступны любому XSS. Переезд на httpOnly-cookie требует CSRF-защиты (SameSite недостаточен для POST из сторонних сценариев) и ломает текущий мобильный/PWA-клиент, который ходит на API напрямую.
- Решение: для закрытого контура (клиника, один tenant, без пользовательского контента в UI) оставляем localStorage, но фиксируем риск здесь. Смягчения, которые уже действуют: React экранирует вывод, `markdown` рендерится без `dangerouslySetInnerHTML` сырого HTML, CSP-заголовки на reverse-proxy (в `GO_LIVE_CHECKLIST.md`), короткое время жизни access-токена + отзыв на сервере (`auth()` сверяет с БД, DECISIONS §1.4.0).
- Триггер пересмотра: появление любого пользовательского HTML в интерфейсе, второй tenant или публикация за пределы клиники. Тогда — httpOnly-cookie + double-submit CSRF + отдельный `/auth/csrf`.

## #31 (2026-10-21): приложения КР — отдельный раздел `appendix`, а не глава
- Факт: 109 чанков из 1073 (10 %) несли чужой раздел, потому что заголовки «Приложение А1/А2/А3/Б/В/Г1-ГN» не совпадали ни со строгим regex, ни с ключевыми словами мягкого правила. Второй врач на тот же вопрос получал `cached: true` и session_id ПЕРВОГО врача; его следующий короткий вопрос (`expand_query`) подмешивал препарат из чужого диалога. Плюс попадание в кэш не писалось в `query_log`, то есть выпадало из аудита и из истории врача.
- Решение: автор входит в ключ (`chat|<uid>|…`), `session_id` в кэш не кладётся — на попадании выдаётся новая сессия, попадание логируется. Гость (`uid="guest"`) кэшируется отдельным ключом, но без session_id, поэтому унаследовать чужой диалог нельзя.
- Отвергнуто: отключить кэш целиком (теряется основная экономия на повторных вопросах) и «кэшировать только для авторизованных» (гостевой чат — основной сценарий демо).
- Оговорка: кэш по-прежнему процесс-локальный; при нескольких воркерах доля попаданий падает, но корректность не страдает.

## #33 (2026-10-21): домен-гейт по трём классам маркеров
- Факт: маркеры «доза», «дозировк», «мг/кг», «ребёнок», «детский», «педиатр» были в списке ЛОР-маркеров, поэтому «доза инсулина ребёнку» считалось ЛОР-вопросом и получало ответ по ближайшему протоколу. Короткие «ух»/«уш»/«нос» искались подстрокой с границей только слева: «ушиб колена», «ухудшение после инфаркта», «носит ли маску» проходили гейт.
- Решение: длинные маркеры (≥5 символов) — подстрока; короткие — начало слова (как было); три особо шумных («ух», «уш», «нос») — строгий набор словоформ с правой границей слова. Дозировочная лексика удалена, названия препаратов оставлены: «доза амоксициллина ребёнку» по-прежнему проходит.
- Замер: ложные отказы 0.0 и отсев вне-доменных 1.0 на hold-out до и после; recall@6 0.9091 не изменился. То есть гейт стал строже к мусору, не потеряв ни одного реального вопроса из набора.
- Оговорка: набор из 5 вне-доменных вопросов мал; расширять его нужно в hold-out, а не в golden, иначе словари подгонятся под замер.

## #34 (2026-10-22): буст по нозологии, распознанной из вопроса
- Факт: косинусы e5 сжаты в 0.80–0.87, поэтому внутри одного раздела порядок почти случаен. Раздел маршрутизировался (`section_hint`), нозология — нет. На hold-out четыре вопроса из 22 имели правильный протокол на 6–13 месте, включая «чем лечить острый гнойный средний отит» (первым шёл чанк лечения синусита).
- Решение: `rag/retriever.nosology_hint()` — упорядоченный список правил «текст → название протокола», первое совпадение побеждает; чанки этого протокола получают множитель `NOSOLOGY_BOOST` (1.15), как раньше получали разделы. `score` не меняется (честный косинус), иначе гейт отказа врал бы.
- **Молчание — часть контракта.** При неоднозначности возвращается None и буст не применяется: неверная нозология хуже отсутствия, потому что поднимает чужой протокол выше правильного. На 70 in-domain вопросах трёх наборов — 0 ложных срабатываний.
- Порядок правил — часть логики, а не оформление: травма носа обязана проверяться раньше деформации перегородки («травма носа с гематомой перегородки» иначе уходила в деформацию и на свежем наборе роняла recall@6 с 0.944 до 0.889).
- Приложения (`appendix`) из-под буста выведены: административный раздел того же протокола не отвечает на клинический вопрос, но всплывал первым.
- Отвергнуто: определять нозологию по топу выдачи (голосование нозологий) — усиливало бы доминирующую, то есть часто неверную; эмбеддинги названий протоколов — тот же сжатый диапазон, что уже не различает нозологии в поиске.
- Оговорка: hold-out перестал быть чистым out-of-sample для этого изменения (правила писались при видимом наборе). Для честной оценки добавлен `lor_retrieval_fresh.json`; на нём прирост скромнее (recall@6 без изменений, MRR 0.941 → 1.000).

## #35 (2026-10-22): сравнение нозологий — нормализованное, а не точное
- Факт: названия нозологий берутся с первой страницы PDF и у 21 протокола из 22 несут хвостовой пробел (`'Отит средний острый '`). Фильтр клиента `filters={"nosology": ...}` сравнивал строки точно, поэтому молча отбрасывал все чанки — работал ровно один протокол из 22, тот, где пробела не было. Тот же дефект обнулял бы и буст по нозологии.
- Решение: `_norm_nos()` (схлопывание пробелов + casefold) во всех сравнениях и чистка названий при загрузке индекса; в пайплайне — `.strip()` при формировании метаданных. Переиндексация не требуется: старые индексы работают как есть.
- Отвергнуто: переиндексация корпуса ради пробела — 76 с на эмбеддинги и бинарный диф ради косметики, при том что нормализация закрывает и старые индексы.

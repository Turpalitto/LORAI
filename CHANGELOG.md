# CHANGELOG — LORAI

## [1.7.0] — 2026-10-21 — разметка разделов по вёрстке PDF (и почему реранкер выключен)

Аудит §4.3, пункт «разметка разделов остаётся эвристикой». Тесты: backend 179, frontend 36.

### Исправлено
- **Разделы протокола размечались по строкам, а не по главам.** `_HEADING_RX` требовал, чтобы строка целиком равнялась названию главы, поэтому реальные главы КР терялись: «Медицинская реабилитация» (в regex есть только «реабилитация»), «Cимптомы, течение» (в исходнике латинская C). Теперь `pdf_loader` отдаёт `headings` — строки, набранные крупнее основного кегля (17.5–20.2 pt против 10.4–12 pt), а чанкер для подтверждённых вёрсткой заголовков применяет мягкое правило. Основной кегль считается как мода по числу символов, а не среднее (иначе заголовки сдвигают порог).
- **`.txt`-протокол индексировался мохнатым текстом.** `fitz.open()` не падает на текстовом файле, а читает UTF-8 как latin-1. Теперь до открытия проверяется сигнатура `%PDF-`.
- **Приложения (Приложение А/Б) наследуют раздел последней главы** — осталось, вынесено в `KNOWN_ISSUES`.

### Измерено (docs/RETRIEVAL_EVAL.md §8.5, §9)
Индекс пересобран: 1084 → 1073 чанка, доля обзорных `general` 3.6 % → 0 %.

| Набор | было | стало |
|---|---|---|
| hold-out recall@6 | 0.8636 | **0.9091** |
| hold-out protocol+section@6 | 0.8636 | **0.9091** |
| hold-out recall@1 | 0.7273 | **0.7727** |
| hold-out MRR@6 | 0.9079 | 0.9000 |
| golden recall@6 | 0.9333 | **0.9667** |
| golden MRR@6 | 0.8286 | **0.8305** |

### Вывод по реранкеру (1.6.0)
Весь прирост, который в 1.6.0 приписывался реранкеру, дала разметка разделов: он вытягивал в топ-6 чанки, лежавшие не в своём разделе. На новом индексе реранкер **не меняет ни одной метрики** (0.9091 / 0.9000 / 0.7727 с ним и без него), поэтому выключен по умолчанию, а в локальном `.env` — закомментирован. Код оставлен: включается одной переменной, понадобится на большем корпусе.

- Тесты: `test_section_headings.py` (7) — мягкое правило по вёрстке, строгий regex как fallback, гомоглиф в заголовке, отброс библиографии, реальный PDF с крупным кеглем, `.txt` без мохнатого текста.

## [1.5.0] — 2026-10-21 — валидатор схем PASS/REVIEW/REJECT, быстрый цикл тестов

Четвёртый проход по аудиту (`docs/AUDIT_2026-10-19.md`, §4.3–4.4). Тесты: backend 153, frontend 35.

### Добавлено
- **`POST /regimen/validate` + `app/clinical/validator.py`** — вердикт по разобранной схеме: **PASS / REVIEW / REJECT**. Перенос гейтов 1–3 из `REGIMEN_VALIDATION_GATES.md` (antibio-calc) в объёме, который LORAI может проверить детерминированно: препарат распознан, доза есть и переводится в мг, кратность и курс найдены, путь введения известен, диапазоны помечены, разовая/суточная доза не выше переданного потолка.
- **Главный инвариант — вердикт только понижается.** PASS ставится, лишь когда пройдены все проверки: иначе «зелёный» вердикт на неполной схеме читается врачом как «проверено и безопасно». Тест `test_verdict_is_the_worst_check_and_never_upgrades` фиксирует это параметризованно.
- **Страница «Схема» в UI** (`#/regimen`): текст из протокола → вердикт, список замечаний, разово/в сутки в мг, раскрывающийся список всех проверок, копирование вердикта, переход в чат.
- **Маркер `slow`** в `pytest.ini`: `test_retrieval_routing.py` (подъём модели e5) помечен целиком. Быстрый цикл — `pytest -m "not slow"`, полный набор — без фильтра.
- Тесты: `backend/tests/test_clinical_validator.py` (21).

### Чего в валидаторе сознательно нет
- **Таблицы максимальных доз по препаратам.** В LORAI нет сертифицированного источника — потолки передаёт вызывающая сторона (`max_single_mg` / `max_daily_mg`), как в `/dosage`. Выдуманный потолок хуже его отсутствия: он даёт ложную уверенность.
- **Проверки взаимодействий** — данных о взаимодействиях в корпусе нет (в antibio-calc этот гейт тоже помечен как невыполнимый).
- **Беременности, почечной функции, возраста** — этих полей в разборе нет, «по умолчанию безопасно» не подставляется. Вес для доз «мг/кг» без явного значения даёт REVIEW, а не «примерно 70 кг».

### Изменено
- `docs/DECISIONS.md`: #28 (валидатор), #29 (JWT в localStorage — зафиксированный компромисс и триггер пересмотра), #30 (маркер `slow`).

## [1.4.0] — 2026-10-19 — учётки в БД, журнал действий, health без внутренностей

Третий проход по аудиту (`docs/AUDIT_2026-10-19.md`, §4). Тесты: backend 130 (было 118), frontend 35.

### Исправлено
- **Пользователи жили в памяти процесса.** `USERS` собирался из env при старте: добавить врача — правка `.env` + рестарт, сменить пароль — то же. Теперь таблица `users` (миграция `0004_users_audit`), env — только первичный сид при пустой таблице. Пароли — PBKDF2, наружу не отдаются.
- **Отзыв доступа не действовал до истечения токена (8 часов).** Роль бралась из JWT. Теперь `auth()` сверяет учётку с БД: отключённый пользователь получает 403 сразу, понижение роли действует немедленно.
- **`/health` без авторизации отдавал внутренности**: число документов и чанков, режим LLM, содержимое кэша, текст ошибки БД. Публичный `/health` теперь отдаёт только `ok/degraded` и версию, детали — в `/admin/health` под авторизацией.
- **Не было аудита действий.** Кто загрузил протокол, кто менял нозологию, кто создал врача — не знал никто. Таблица `audit_log`: вход (успешный и неудачный), загрузка/разбор/правка протокола, управление учётками, ручная очистка.
- **Гонка при параллельной загрузке.** Два одновременных аплоада одного файла проходили проверку дедупликации до того, как любой из них создавал запись, и создавали **две** карточки на один файл. Плюс запись индекса использовала общий `<path>.tmp`: два сохранения затирали файл друг друга, второе падало с `ENOENT` на `rename`. Теперь дедуп и создание — под замком по имени файла, разбор — под замком по `document_id`, temp-файл уникальный (`pid` + `uuid`). Проверено тремя параллельными загрузками: одна запись, чанки на месте, в логе нет ошибок записи.

### Добавлено
- **Управление учётками через API и админку**: `GET/POST /admin/users`, `PATCH /admin/users/{email}` (роль, активность, ФИО, пароль). Защита от самоблокировки: нельзя отключить/понизить себя и оставить систему без активного администратора.

- **Request-id**: middleware принимает `X-Request-ID` (с валидацией — иначе инъекция в лог), генерирует свой, возвращает в заголовке и пишет в каждую строку лога. Необработанные исключения отдают 500 с `request_id` вместо голого «Internal Server Error».
- **Политика хранения**: `QUERY_RETENTION_DAYS=90` (тексты запросов), `AUDIT_RETENTION_DAYS=365`, очистка при старте + `POST /admin/maintenance/purge`. ПДн-фильтр на входе не абсолютен — бессрочное хранение клинического текста было лишним риском.
- В админ-панели — блок «Пользователи и журнал действий»: создание врача, включение/отключение, смена роли и пароля, последние 50 записей журнала.
- Тесты: `backend/tests/test_users_audit_health.py` (12).

## [1.3.1] — 2026-10-19 — аудит: единый чанкер на загрузке, проверка чисел, клинический нормализатор

Полный отчёт: `docs/AUDIT_2026-10-19.md`. Тесты: backend 113 (было 90), frontend 35.

### Исправлено
- **Загрузка через админку индексировала документ старым чанкером.** `process_pdf()` собирал разделы через `detect_sections()` (обрезка до 6000 символов) и дублировал весь документ в `general`. Замер на КР «Аллергический ринит»: 128 чанков, **88 % `general`** против 95 чанков и 2 % у `build_index_chunks()`. Теперь загрузка и офлайн-пересборка используют один чанкер; `sections.*.raw` собираются из тех же чанков.
- **`check_numbers` пропускал ошибку в 100 раз.** Число искалось подстрокой: «5 мг» проходило при источнике «500 мг». Теперь сравнение по границам токена, с поддержкой разрядных пробелов («1 000» = «1000»).
- **Path traversal в `POST /admin/upload`.** `raw_dir / f.filename` писал файл по клиентскому пути с `../`. Теперь используется только `basename` (и для дедупа, и для temp-файла, и для записи).
- **У `/auth/login` не было лимита попыток** (на `/chat` был). Добавлен троттлинг неудачных попыток: 5 промахов за 5 минут на пару (IP, email) → 429; успешные входы не считаются, клиника за NAT не блокируется.
- **ПДн-фильтр блокировал «фамилия врача в протоколе…»** — слово `фамилия` убрано из триггеров, форматы идентификаторов и пример «Иванов» сохранены.

### Добавлено
- **Пакет `backend/app/clinical/` — перенос детерминированной нормализации из `antibio-calc`**: словари синонимов препаратов (120 → МКН), путей введения (40), единиц (33), 53 правила кратности и 10 правил курса. Диапазон («2–3 раза», «5–7 дней») → нижняя граница + флаг `is_range`.
- **`POST /regimen/parse`** — разбор схемы из текста протокола без LLM: препарат → МКН, доза (мг, мг/кг), кратность, курс, путь введения, суточная доза, `confidence`, `warnings`.
- **`POST /drug-check`** нормализует названия перед поиском и возвращает `drugs_normalized` (Флемоксин → Амоксициллин), иначе предостережения по бренду не находились.
- **`POST /dosage`** считает `doses_per_day` и `daily_mg` из строки кратности; добавлен флаг `capped` при срабатывании потолка разовой дозы.
- Тесты: `backend/tests/test_clinical_normalizer.py` (23 теста).

### Второй проход: приоритеты из аудита (приватность, схема, устойчивость)

- **История запросов стала персональной.** В `query_log` появилась колонка `user` (миграция `0003_query_log_user`), `/chat` и `/chat/stream` принимают токен «мягко» и пишут автора (`guest` без токена). `GET /history` по умолчанию отдаёт только свои запросы; `?scope=all` — админу, врачу 403. Раньше любой вошедший видел запросы всей клиники.
- **Схема БД приводится к head миграциями** (`app/core/migrations.py`), `create_all` остался только в тестах. БД, созданная прежним `create_all`, штампуется на `0002` и догоняется до head; миграция `0003` идемпотентна. Локальная `lorai.db` смигрирована (бэкап рядом), 209 старых запросов помечены `legacy`.
- **Загрузка протокола стала фоновой.** `POST /admin/upload` отвечает `202` с `document_id` и `status=processing`, разбор идёт в `BackgroundTasks`; при ошибке документ помечается `failed`, а не теряется. Админка опрашивает `/protocols/{id}` и показывает «обрабатывается». Раньше 70-страничный PDF занимал воркер на всё время разбора.

- **Синглтон `VectorStore` под `threading.Lock`** — два первых одновременных запроса больше не грузят модель дважды.
- **Просроченные сессии диалога подчищаются** (`_prune` при превышении 500 записей) — раньше словарь рос без границ.
- Тесты: `backend/tests/test_schema_and_privacy.py` (5 тестов), всего 118.

## [1.3.0] — 2026-10-07 — поиск: embeddings, маршрутизация по разделам, корпус без дублей

Полные измерения и оговорки: `docs/RETRIEVAL_EVAL.md`, решение: DECISIONS #26.

### Исправлено
- **Ложные отказы на реальных ЛОР-вопросах: 20 % → 0 %.** Домен-гейт не знал «ё» («ребёнка» ≠ «ребен»), не имел лексики «эпиглоттит/круп/стридор/тризм/глотание/оталгия», а «паратонзиллярный» перестал находиться при переходе на поиск с начала слова. Теперь: нормализация «ё», расширенный словарь, длинные маркеры — подстрокой, короткие — с начала слова. Вне-доменные вопросы по-прежнему отсекаются 100 %.
- **Корпус поиска на 84 % состоял из дублей** (1304 из 1599 чанков — `general`, разделы покрывали ~17 % текста): из-за этого в топ-6 попадали обзорные куски, и модель отвечала «в контексте нет информации». Индекс пересобран из PDF (`scripts/reindex_corpus.py`): документ покрыт ровно один раз, чанки помечены разделом и реальными страницами. SQLite не тронут, бэкап прежнего индекса сохранён.
- `VECTOR_BACKEND` из `.env` игнорировался: стор читал только переменные окружения, а не настройки pydantic.

### Добавлено
- **Получить по вопросу нужный раздел протокола**: `section_hint()` в `rag/retriever.py` + `section_boost` и ограничение обзорных чанков (`GENERAL_CHUNK_CAP`) в поиске. Единая точка `retrieve()` — приложение и замер используют один код.
- **Эмбеддинги как рабочий бэкенд**: `intfloat/multilingual-e5-base` (`VECTOR_BACKEND=embeddings`), префиксы query/passage, персистентный индекс, устройство MPS/CUDA/CPU, кэш модели внутри проекта (`data/hf_cache`), честный откат на TF-IDF с причиной в `/health`.
- **`effective_threshold()`**: порог скора зависит от шкалы бэкенда (TF-IDF 0.12 / эмбеддинги 0.80) — у e5 даже нерелевантный текст даёт 0.83–0.85.
- **Замер как часть проекта**: `data/eval/lor_retrieval_golden.json` (30 ЛОР-вопросов + 6 вне-доменных), `scripts/eval_retrieval.py` (recall@k, MRR, покрытие разделов, «протокол+раздел», отказы, скоры), `scripts/eval_answers.py` (ответ-уровень на реальных вызовах LLM), `scripts/reindex_corpus.py`, `scripts/reindex_embeddings.py`.
- `/health` отдаёт состояние поиска (`retrieval.backend`, `vectors_indexed`); дашборд показывает врачу, работает ли семантический поиск.
